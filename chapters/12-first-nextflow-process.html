22  Your first Nextflow process

22.1 Why a biologist should care

The safest way to learn a workflow language is to remove the biology briefly. If a one-line command fails, you can focus on Nextflow rather than wondering whether the reference genome, sample chemistry or tool parameters are wrong.

22.2 Engineering objective

Run one process, locate its task directory, inspect the exact command, verify the output and rerun it from cache.

22.3 Before you type

Verify Java and Nextflow:

java -version
nextflow -version

Then enter the examples directory from the book repository:

cd examples/nextflow-basics
pwd
ls 01-hello.nf

Do not run computational tutorials on an HPC login node if local policy forbids Java or analysis processes there. Request a small compute allocation.

22.4 Build it: read the complete file

Open 01-hello.nf:

nextflow.enable.dsl=2

params.name = 'biologist'

process MAKE_GREETING {
    tag "${name}"
    publishDir 'results/01-hello', mode: 'copy'

    input:
    val name

    output:
    path 'greeting.txt'

    script:
    """
    echo "Hello, ${name}!" > greeting.txt
    """
}

workflow {
    MAKE_GREETING(params.name)
}

22.4.1 Read the syntax

  • nextflow.enable.dsl=2 makes the DSL generation explicit for learners.
  • params.name declares a command-line parameter with a default.
  • MAKE_GREETING is the process definition.
  • tag places a meaningful value in logs instead of only a task hash.
  • val name accepts an ordinary value.
  • path 'greeting.txt' declares the file that success must produce.
  • the triple-quoted block is the shell script.
  • MAKE_GREETING(params.name) invokes the process in the workflow.
  • publishDir ... mode: 'copy' copies the selected result out of work/.

This book uses process-level publishDir because it remains common in production and nf-core pipelines and is supported by the validated tutorial version. Newer Nextflow training also teaches workflow-level output publishing; learn to recognize both and follow the version policy of the project you join.

22.5 Run it

nextflow run 01-hello.nf --name Ada

Why two dashes before name: pipeline parameters use --. Core Nextflow options such as -resume, -profile and -with-trace use one dash.

Expected status shape:

[ab/cdef12] MAKE_GREETING (Ada) | 1 of 1 ✔

The hash will differ. Verify the published result:

cat results/01-hello/greeting.txt

Expected:

Hello, Ada!

22.6 Inspect task anatomy

Ask Nextflow for the most recent task directory:

nextflow log last -f hash,name,status,workdir

Copy the printed work-directory path into a variable:

TASK_DIR=/absolute/path/printed/by/nextflow
ls -la "$TASK_DIR"

Inspect evidence one file at a time:

cat "$TASK_DIR/.command.sh"
cat "$TASK_DIR/.command.log"
cat "$TASK_DIR/.exitcode"
  • .command.sh is the scientific command generated for the process.
  • .command.run is Nextflow’s execution wrapper, including staging/runtime.
  • .command.out and .command.err capture standard streams.
  • .command.log combines task output useful for diagnosis.
  • .exitcode should contain 0 for success.

Do not edit files in a task directory to “fix” a run. Fix tracked pipeline code or configuration, then rerun.

22.7 Prove caching

Run the same command with -resume:

nextflow run 01-hello.nf --name Ada -resume

Expected status includes cached: 1.

Now change the input value:

nextflow run 01-hello.nf --name Grace -resume

This creates a new task because an input changed. Cache reuse is based on task identity, not merely the process name.

22.8 What changed on disk

After the first run you should have:

.nextflow.log
.nextflow/
work/
results/01-hello/greeting.txt

The hidden metadata and work/ support history, diagnosis and resume. They are normally ignored by Git.

22.9 Common failures

22.9.1 nextflow: command not found

The launcher is absent or not in PATH. Return to the setup chapter and verify command -v nextflow.

22.9.2 Java fails before the pipeline starts

Nextflow itself requires Java. On HPC, load a validated Java module inside a compute allocation and place NXF_HOME on a filesystem with adequate quota.

22.9.3 Output already exists

Repeated publishing may overwrite or conflict depending on publish settings and Nextflow version. Use a new result directory for independent production runs; use -resume for continuation of the same run.

22.10 Verification checkpoint

Pass only if:

test "$(cat results/01-hello/greeting.txt)" = 'Hello, Grace!'
nextflow log last -f name,status

The shell test must exit zero and the latest task must be COMPLETED or CACHED as appropriate.

22.11 Commit checkpoint

In your practice repository, a useful message would be:

git add 01-hello.nf
git commit -m "feat: add first Nextflow greeting process"

Never commit work/, .nextflow/ or large generated results.

22.12 Try it yourself

Add a --species parameter and produce Hello, Ada! Species: mouse. Predict whether changing only --species with -resume should create a new task.

22.13 What to remember

  • Pipeline parameters use --; Nextflow options use -.
  • A declared output is part of the process contract.
  • The work hash points to task evidence.
  • -resume reuses only matching successful work.

22.14 Interview grill

  1. What launches the process in this file?
  2. Why is name a val rather than a path?
  3. What proves the shell command ran successfully?
  4. What happens if greeting.txt is not created?
  5. Why is tag useful in a cohort?
  6. Which directory supports resume?
  7. Why should task files not be edited manually?
  8. What invalidates the cached greeting task?
  9. How do pipeline parameters differ from core options?
  10. What does publishing add beyond a work-directory output?
