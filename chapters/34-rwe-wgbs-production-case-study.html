34  Real-world case study: production WGBS with nf-core/methylseq

By the end of this bonus chapter, you will be able to:

  • turn a multi-terabyte WGBS request into staged engineering questions;
  • explain why smoke tests, data pilots and complete-sample qualification are different;
  • configure nf-core/methylseq for Bismark on Slurm with containers;
  • diagnose failures across Java, Nextflow, plugins, storage, containers and references;
  • use measured traces to plan memory, runtime and cohort concurrency;
  • explain why routine FASTQ/chromosome splitting is not the default design; and
  • define the evidence required before scaling from one sample to a cohort.

34.1 Why a biologist should care

Tutorial datasets finish in minutes. Production WGBS datasets can contain billions of paired reads, terabytes of compressed FASTQs and tasks that run for days. At that scale, a small misunderstanding becomes expensive:

  • using the wrong reference index can invalidate alignment;
  • launching Java on a restricted login node can crash before Nextflow starts;
  • storing framework and image caches in a small home quota can corrupt downloads;
  • interpreting two Slurm task jobs as two samples can cause unnecessary intervention;
  • deduplicating independent chunks before merging can change the biological result;
  • deleting work/ too early can turn a recoverable interruption into a complete rerun; and
  • scheduler completion can be mistaken for a validated methylation dataset.

This chapter reconstructs a real engineering qualification in sanitized form. It is a real-world evidence (RWE) operations case study, not clinical validation and not a replacement for the official pipeline documentation.

34.2 Case scope

The project contained 30 paired-end human WGBS samples:

30 biological samples
× 2 mates per sample
= 60 compressed FASTQ files
≈ 3.7 TB total compressed input

Individual FASTQs were approximately 47–88 GB. A representative pair was about 101 GB compressed with 151-base reads.

The required deliverables were:

  • raw and trimmed read QC;
  • Bismark alignment to GRCh38;
  • whole-sample duplicate removal;
  • coordinate-sorted BAM and BAI;
  • Bismark methylation coverage (.cov.gz);
  • Bismark reports and summary;
  • MultiQC; and
  • reproducible execution and provenance evidence.

The portable implementation used nf-core/methylseq 4.2.0, Nextflow, Singularity and Slurm.

34.3 The decision ladder

The team did not begin by submitting all 30 samples:

host prerequisites
        ↓
tiny nf-core smoke test
        ↓
10M-pair real-data pilot
        ↓
one complete-sample qualification
        ↓
review MultiQC + trace + storage + provenance
        ↓
30-sample production cohort

Each gate answers a different question.

Gate Question answered What it cannot establish
Environment check Can Java, Nextflow, Slurm and Singularity start? Biological correctness
nf-core test profile Can the workflow, containers and executor communicate? Human-genome performance
10M real-data pilot Are real reads/reference compatible, and what is approximate throughput? Complete-sample QC and exact wall-time
One complete sample Do whole-sample outputs, QC, runtime, memory and storage pass? Cohort-wide sample variation
Cohort Can all samples complete under reviewed capacity policy? Automatic scientific interpretation

34.4 Architecture selected

paired FASTQs
    ├── FastQC
    └── Trim Galore
            ↓
       Bismark alignment
            ↓
       whole-sample deduplication
            ↓
       SAMtools sort + index
            ↓
       Bismark methylation extraction
            ↓
       Bismark reports + MultiQC

The workflow logic came from versioned nf-core/methylseq. Site configuration selected Slurm and Singularity without editing the upstream pipeline.

34.5 Why the initial chunking plan was reconsidered

The first idea was:

split FASTQ into 10M-read chunks
→ align chunks
→ merge BAMs
→ split BAM by chromosome
→ extract methylation

Chunking alignment can reduce the wall-time of one enormous task, but it adds new correctness and operations obligations:

  • R1/R2 records must remain synchronized;
  • chunk identity must remain attached to the biological sample;
  • every alignment must use identical software, reference and parameters;
  • read groups and headers must be compatible before merge;
  • all chunks must be merged before one global sample-level deduplication;
  • missing or duplicate chunks must be detected;
  • merged and unsplit results require equivalence testing;
  • task count, I/O and temporary storage rise substantially; and
  • chromosome splitting can complicate paired reads and cross-contig behavior.

The dangerous design is to deduplicate each chunk independently and merge the results. Duplicates occurring in different chunks cannot see one another, so the final duplicate set may differ from whole-sample deduplication.

The default decision was therefore:

Process each biological sample as one paired dataset with the established nf-core/methylseq workflow. Consider chunked alignment only if measured complete-sample tasks exceed site limits, and merge before one global deduplication step.

This is an evidence-based default, not a claim that chunking is universally wrong.

34.6 Phase 1: establish a usable host environment

34.6.1 Inventory before installation

On a compute node, inspect rather than assume:

command -v java
command -v nextflow
command -v singularity
command -v apptainer
module spider java
module spider singularity

The observed cluster supplied Java and Singularity modules but no Nextflow module. The user’s existing Conda Java crashed during JVM initialization. This was a host-runtime failure before any workflow or WGBS code ran.

34.6.2 Lesson: use a validated Java module

source /etc/profile.d/lmod.sh
module purge
module load java/xxx
module load singularity/xxx

java -version
singularity --version

Module names are site-specific. The public repository must use placeholders; the real names belong in an ignored environment file.

34.6.3 Failure: Nextflow framework download exceeded home quota

The first launcher attempt wrote its framework JAR below a small home directory and failed with Disk quota exceeded, leaving an invalid/corrupt JAR.

The correction was to put the runtime home on project storage:

export PROJECT=/project/xxx/wgbs-project
export NXF_HOME="$PROJECT/nextflow_home"
export NXF_VER=25.10.7
export NXF_TEMP="$PROJECT/tmp"

mkdir -p "$NXF_HOME" "$NXF_TEMP"

NXF_HOME stores Nextflow framework and asset data. It is not the same as the pipeline’s work/ directory.

34.6.4 Failure: launcher location and framework version were confused

The small nextflow launcher script and the downloaded framework JAR are different files. Running ./nextflow works only from the directory containing the executable launcher, or through its absolute path:

/project/xxx/wgbs-project/bin/nextflow -version

Verify the version under the same NXF_HOME and NXF_VER that production will use.

34.6.5 Failure: incompatible Nextflow/plugin versions

An early pinned Nextflow release was too old for the nf-schema plugin required by methylseq. Jumping to a newer unvalidated framework exposed a separate legacy configuration-parsing incompatibility. The working response was not “always use latest”; it was to identify and pin a compatible combination, then test it.

The qualification recorded:

Nextflow:          25.10.7
nf-core/methylseq: 4.2.0
Singularity CE:    4.0.3
Bismark:           0.25.1 (containerized task)

These are case-study facts, not permanent universal requirements.

34.7 Phase 2: configure container storage

Container pulls and OCI-to-SIF conversion are too large for many home quotas:

export NXF_SINGULARITY_CACHEDIR="$PROJECT/singularity_cache"
export SINGULARITY_CACHEDIR="$PROJECT/singularity_cache"
mkdir -p "$SINGULARITY_CACHEDIR"

Test one small container on a compute node:

singularity exec \
  docker://quay.io/biocontainers/seqkit:2.8.2--h9ee0642_0 \
  seqkit version

Container conversion logs may contain alarming informational messages. The acceptance evidence is the final exit status and expected tool version, not one isolated line.

34.8 Phase 3: run the tiny nf-core smoke test

The smoke test used versioned pipeline and container profiles:

nextflow run nf-core/methylseq \
  -r 4.2.0 \
  -profile test,singularity \
  -c conf/slurm.config \
  --outdir results/nfcore-test \
  -work-dir work \
  -with-trace logs/smoke.trace.tsv \
  -with-report logs/smoke.report.html \
  -with-timeline logs/smoke.timeline.html

The test profile downloaded a tiny test genome and built the matching Bismark index inside a task work directory. This explains how alignment succeeded even though the project’s human reference did not yet contain Bisulfite_Genome.

Smoke-test acceptance required:

find results/nfcore-test -type f -name '*.cov.gz' -print
find results/nfcore-test -type f -name '*.bam' -print
find results/nfcore-test -type f -name 'multiqc_report.html' -print

The test proved workflow plumbing and expected output types. It did not prove that the human GRCh38 reference was ready.

34.9 Phase 4: prepare the correct Bismark reference

The existing GRCh38 directory contained BWA and BWA-Meth indexes. Those cannot substitute for a Bismark/Bowtie2 bisulfite index.

A valid Bismark reference directory has this shape:

bismark_species_assembly/
├── reference.fa
└── Bisulfite_Genome/
    ├── CT_conversion/
    │   ├── BS_CT.1.bt2
    │   ├── ...
    │   └── BS_CT.rev.2.bt2
    └── GA_conversion/
        ├── BS_GA.1.bt2
        ├── ...
        └── BS_GA.rev.2.bt2

The FASTA was copied—not symlinked—into the self-contained index directory so the same path remained visible inside container bind mounts. Its checksum was verified before and after copying:

sha256sum reference.fa

The index was built through a Slurm task using the same containerized Bismark version as the workflow. Acceptance required all 12 Bowtie2 index files and the matching FASTA. A partial Bisulfite_Genome from a failed attempt was preserved with a .failed.JOB_ID suffix for diagnosis rather than presented as valid.

For another species, repeat the procedure with that species and assembly. Never reuse a human index for mouse, or an index from another assembly release.

34.10 Phase 5: create a synchronized 10M-pair pilot

The pilot sampled the same first 10,000,000 records from R1 and R2:

seqkit head --number 10000000 SAMPLE_R1.fastq.gz \
  --out-file SAMPLE_10M_R1.fastq.gz

seqkit head --number 10000000 SAMPLE_R2.fastq.gz \
  --out-file SAMPLE_10M_R2.fastq.gz

Verification:

seqkit stats SAMPLE_10M_R1.fastq.gz SAMPLE_10M_R2.fastq.gz
gzip -t SAMPLE_10M_R1.fastq.gz SAMPLE_10M_R2.fastq.gz

Both mates contained exactly 10,000,000 reads of length 151. Taking the same record count from ordered mates preserves pairing without loading complete FASTQs into memory.

34.10.1 Pilot samplesheet

sample,fastq_1,fastq_2,genome
SAMPLE_10M,/project/xxx/subsets/SAMPLE_10M_R1.fastq.gz,/project/xxx/subsets/SAMPLE_10M_R2.fastq.gz,

34.10.2 Pilot parameters

input: /project/xxx/samplesheets/SAMPLE_10M.csv
outdir: /project/xxx/results/SAMPLE_10M

aligner: bismark
fasta: /project/xxx/reference/bismark_grch38/reference.fa
bismark_index: /project/xxx/reference/bismark_grch38

Resource policy belongs in Nextflow configuration, not invented YAML keys. The pipeline’s Bismark alignment defaults requested 12 CPUs and 72 GB, with an eight-day task ceiling.

34.11 Measured pilot evidence

The 10M-pair workflow completed successfully:

Metric Measured value
Workflow wall-time 2 h 3 m 44 s
Total CPU consumption 24.6 CPU-hours
Bismark alignment runtime 1 h 45 m 52 s
Alignment CPU utilization 1168.1% with 12 CPUs (~97% effective use)
Alignment peak RSS 38.9 GB
Alignment read I/O 126.9 GB
Alignment write I/O 81.4 GB
Deduplicated BAM 1.16 GB
BAM index 2.21 MB
Methylation coverage 39.2 MB compressed
MultiQC report 2.41 MB

Alignment dominated runtime. This justified focusing capacity planning on Bismark rather than prematurely optimizing very short reporting tasks.

34.11.1 What the pilot can and cannot say

Useful evidence:

  • compatible reference/index and real WGBS reads;
  • tool/container compatibility;
  • approximate alignment throughput;
  • CPU efficiency and peak memory;
  • expected output types; and
  • preliminary storage/I/O behavior.

Not final biological evidence:

  • whole-sample duplication rate;
  • genome/CpG coverage distribution;
  • complete mapping behavior;
  • final methylation conclusions; or
  • exact whole-sample duration.

34.12 Projection to a complete sample

The representative full pair contained 100.83 GB compressed versus 1.327 GB for the pilot, a ratio of about 75.97.

Simple linear projection:

complete alignment ≈ pilot alignment × 75.97 ≈ 5.6 days
complete workflow  ≈ pilot workflow  × 75.97 ≈ 6.5 days

Planning range: approximately 6–8 days, excluding queue delay and retries. This is a model, not a promise; compression, trimming, duplication, filesystem contention and sample complexity may scale nonlinearly.

34.13 Phase 6: create reusable production controls

34.13.1 Private site environment

PROJECT=/storage/xxx/wgbs-production
JAVA_MODULE=java/xxx
CONTAINER_MODULE=singularity/xxx
CONTAINER_PROFILE=singularity
NEXTFLOW_VERSION=25.10.7
METHYLSEQ_VERSION=4.2.0
NEXTFLOW_BIN=/absolute/path/to/bin/nextflow

This real file is ignored by Git. A tracked .example file contains only placeholders.

34.13.2 Shared-cluster concurrency policy

process {
    withName: BISMARK_ALIGN {
        maxForks = 10
    }
}

executor {
    queueSize = 30
    submitRateLimit = '2 sec'
}

Interpretation:

  • at most ten Bismark alignment tasks run concurrently;
  • up to 30 tasks may be managed in the executor queue; and
  • submissions are rate-limited as scheduler courtesy.

With 12 CPUs and 72 GB requested per alignment, ten concurrent alignments imply up to 120 CPUs and 720 GB requested memory. The policy was chosen to avoid occupying an entire shared cluster.

34.14 Capacity planning for 30 samples

Idealized cohort makespan from the pilot projection:

Concurrent alignments Idealized cohort time
1 195.8 days
3 65.3 days
5 39.2 days
10 19.6 days
30 6.5 days

The selected policy was ten, not 30. Shared-resource stewardship was part of the engineering requirement.

The 10M pilot projected approximately 1,869 CPU-hours per full sample and 56,069 CPU-hours for 30 samples. Replace these estimates with complete-sample measurements before final cohort scheduling.

34.15 Phase 7: qualify one complete sample

The complete sample was launched in a separate project root:

/storage/xxx/wgbs-one-sample-production/
├── bin/
├── conf/
├── logs/
├── nextflow_home/
├── params/
├── results/
├── run_manifests/
├── samplesheets/
├── singularity_cache/
├── tmp/
└── work/

The original FASTQs remained in their authoritative location; the samplesheet referenced them without creating another 101 GB copy.

34.15.1 Full-sample parameter file

input: /storage/xxx/wgbs-one-sample-production/samplesheets/SAMPLE_01.csv
outdir: /storage/xxx/wgbs-one-sample-production/results/SAMPLE_01

aligner: bismark
fasta: /storage/xxx/reference/bismark_grch38/reference.fa
bismark_index: /storage/xxx/reference/bismark_grch38

34.15.2 Preflight

The preflight checked:

  • Java, Nextflow, Singularity, Slurm and launcher paths;
  • unused output location;
  • writable output parent;
  • matching FASTA and complete 12-file Bismark index;
  • samplesheet header and one readable R1/R2 pair;
  • unresolved placeholders; and
  • input-scaled free-storage estimate.

Preflight is a convenience gate. It does not replace nf-core schema validation, task checks or biological QC.

34.15.3 Submit

sbatch bin/run_production.sbatch \
  /storage/xxx/wgbs-one-sample-production/params/SAMPLE_01.yaml

The visible wgbs-production job was the Nextflow controller. FastQC and Trim Galore appeared as two simultaneous nf-... Slurm jobs for the same sample. Bismark alignment began only after trimmed reads were available.

34.15.4 Monitor

squeue -u "$USER" -o "%.18i %.55j %.2t %.10M %.30R"
tail -n 60 logs/wgbs-production.JOB_ID.out
tail -n 40 logs/wgbs-production.JOB_ID.err

Repeated Nextflow tables in the captured output were display refreshes, not duplicate submissions. A notice that a newer Nextflow version existed was informational because the project deliberately used a validated pin.

34.16 Complete-sample acceptance gate

The case study was still running when this chapter was written. It must remain labeled in progress, and no complete-sample MultiQC conclusion should be claimed yet.

Acceptance requires:

  1. controller log contains Pipeline completed successfully;
  2. no failed or unresolved task remains;
  3. deduplicated BAM and matching BAI exist and pass format checks;
  4. Bismark .cov.gz exists, is nonempty and passes gzip -t;
  5. Bismark sample report and summary exist;
  6. MultiQC contains the intended sample and is reviewed;
  7. trace records actual runtime, CPU, peak RSS and I/O;
  8. total work/ and results/ storage are measured; and
  9. private provenance/checksum manifest is complete.

Review MultiQC for at least:

  • raw and trimmed read quality;
  • adapter/quality trimming behavior;
  • mapping efficiency;
  • duplicate percentage;
  • methylation-extraction metrics; and
  • missing or unexpectedly duplicated samples.

Do not publish an unredacted report until sample identifiers, paths, command lines and infrastructure details have been reviewed for privacy.

34.17 Run manifests and checksums

For every pilot and production execution, retain a private manifest containing:

  • analysis purpose and operator;
  • controller and task identifiers;
  • repository commit and pipeline revision;
  • Java, Nextflow, container runtime and tool versions;
  • samplesheet and parameter-file copies;
  • SHA-256 checksums for those inputs;
  • reference source, release and FASTA checksum;
  • exact command and configuration layers;
  • exceptions/deviations;
  • trace/report/timeline/DAG paths;
  • required-output checks; and
  • QC review and approval status.

Checksums provide file-identity evidence. They do not prove that metadata are correct, a method is validated or an output is scientifically acceptable. In a regulated environment, integrate this engineering evidence into the applicable quality system rather than labeling a public tutorial “CLIA validated.”

34.18 Use the companion repository for your own WGBS analysis

The public WGBS methylseq pipeline repository is the reusable implementation behind this case study. A new user can clone or fork it, but cannot safely launch a large cohort without supplying and validating their own infrastructure, reference, inputs and capacity policy.

34.18.1 Clone versus fork

Clone when you want to use the documented workflow without maintaining a public variant:

git clone https://github.com/cjgunase/wgbs-methylseq-pipeline.git
cd wgbs-methylseq-pipeline
git rev-parse HEAD

Fork first when your group intends to maintain reviewed changes, site profiles or additional features. Keep private paths and regulated metadata out of both the original repository and the fork.

Record the commit from git rev-parse HEAD in every run manifest. A Git branch name such as main can move; a commit identifies the code reviewed at launch.

34.18.2 What the repository supplies

Repository component Purpose
bin/check_environment.sh Check host prerequisites and report actionable failures
bin/run_nfcore_test.sbatch Run the tiny bundled methylseq test through Slurm/Singularity
bin/build_bismark_index.sbatch Build a containerized Bismark index from a supplied FASTA
bin/make_samplesheet.sh Generate paired samplesheet rows from regular R1/R2 filenames
bin/run_pilot.sbatch Run a real-data subset with the production-like pipeline
bin/preflight.sh Check paths, pairing, reference/index, output collision and storage
bin/run_production.sbatch Guarded full-sample/cohort Nextflow controller
bin/monitor_run.sh Read-only Slurm/controller progress summary
conf/*.example Portable templates without private site values
params/*.example.yaml Analysis parameter templates
assets/run-manifest.template.md Private execution/provenance record
docs/ Beginner explanations, troubleshooting and acceptance gates

The repository does not supply your sequencing data, reference assembly, scheduler account, storage allocation, Java installation or permission to use the cluster.

34.18.3 Host prerequisites

For a Slurm HPC system, obtain or verify:

  • Java compatible with the selected Nextflow version;
  • a pinned Nextflow launcher/framework;
  • Git and a download tool such as curl;
  • Slurm commands including sbatch and squeue;
  • Singularity or Apptainer allowed by the site;
  • shared storage readable from compute nodes; and
  • sufficient quota for inputs, work/, results, framework and image caches.

Bioinformatics tools such as FastQC, Trim Galore, Bismark and SAMtools are provided by nf-core’s versioned containers. Users normally do not rebuild one large custom container for this workflow. The first run downloads the required images; offline sites must pre-stage them according to local policy.

On a laptop or workstation, follow the repository’s local installation guide and use Docker where supported. Production-scale WGBS generally requires an HPC or cloud environment with adequate storage and scheduler capacity.

34.18.4 Step 1: create the private site environment

From the repository root:

cp conf/site.env.example conf/site.env

Edit the ignored conf/site.env:

PROJECT=/project/xxx/wgbs-pilot
JAVA_MODULE=java/xxx
CONTAINER_MODULE=singularity/xxx
CONTAINER_PROFILE=singularity
NEXTFLOW_VERSION=25.10.7
METHYLSEQ_VERSION=4.2.0
NEXTFLOW_BIN=/absolute/path/to/bin/nextflow

Values shown are placeholders except the versions validated in this case study. If your site requires different versions, treat that as a new compatibility combination: rerun the environment check and smoke test and record the result.

Place PROJECT, NXF_HOME, work data and container caches on an appropriate large filesystem—not automatically in a quota-limited home directory.

34.18.5 Step 2: verify the host on a compute node

Request a small interactive allocation using your site’s documented syntax, then run:

bash bin/check_environment.sh

Proceed only when Java, Nextflow, the container runtime and Slurm tools report OK. A missing bioinformatics executable on the host is not necessarily an error because task software runs in containers.

34.18.6 Step 3: run the tiny infrastructure smoke test

mkdir -p logs
sbatch bin/run_nfcore_test.sbatch

Record the controller job ID, monitor it and require the final success marker. Confirm that the test produces BAM/BAI, .cov.gz, FastQC, Bismark reports and MultiQC. This stage uses nf-core test data and its test reference; it does not validate your species assembly or sequencing data.

34.18.7 Step 4: prepare a species- and assembly-specific reference

Choose a traceable FASTA. Record:

  • species and assembly name/release;
  • authoritative source and retrieval date;
  • primary/alternate/decoy content decisions;
  • chromosome naming convention; and
  • SHA-256 checksum.

Build a self-contained index:

sbatch bin/build_bismark_index.sbatch \
  /absolute/path/to/reference.fa \
  /absolute/path/to/bismark_species_assembly

The destination should contain the FASTA plus Bisulfite_Genome/CT_conversion and GA_conversion, each with six Bowtie2 index files. The index must match the exact FASTA supplied to methylseq.

For mouse, plant or another organism, substitute the correct assembly and build a new index. The workflow is species-independent; the reference is not.

34.18.8 Step 5: prepare and validate input metadata

Expected paired filename pattern for the generator:

SAMPLE_001_R1.fastq.gz
SAMPLE_001_R2.fastq.gz

Generate a samplesheet:

bash bin/make_samplesheet.sh \
  /absolute/path/to/fastq-directory \
  /absolute/path/to/study.samplesheet.csv

Inspect it rather than trusting generation:

head /absolute/path/to/study.samplesheet.csv
wc -l /absolute/path/to/study.samplesheet.csv

The methylseq 4.2.0 paired-end shape used here is:

sample,fastq_1,fastq_2,genome
SAMPLE_001,/data/SAMPLE_001_R1.fastq.gz,/data/SAMPLE_001_R2.fastq.gz,

If filenames do not follow the supported pattern, create and validate the CSV deliberately. Confirm every sample ID, R1/R2 association, file existence, readability and study-metadata mapping. The generator cannot detect a FASTQ that was mislabeled before it reached the directory.

34.18.9 Step 6: run a synchronized real-data pilot

Create the same number of records from R1 and R2 on a compute node. The repository guide uses 10,000,000 read pairs:

seqkit head --number 10000000 SAMPLE_001_R1.fastq.gz \
  --out-file SAMPLE_001_10M_R1.fastq.gz

seqkit head --number 10000000 SAMPLE_001_R2.fastq.gz \
  --out-file SAMPLE_001_10M_R2.fastq.gz

seqkit stats SAMPLE_001_10M_R1.fastq.gz SAMPLE_001_10M_R2.fastq.gz
gzip -t SAMPLE_001_10M_R1.fastq.gz SAMPLE_001_10M_R2.fastq.gz

Copy and edit the pilot parameter template:

cp params/pilot.example.yaml /private/path/pilot.params.yaml

Set input, a new outdir, aligner: bismark, the FASTA and its matching bismark_index. Submit:

sbatch bin/run_pilot.sbatch /private/path/pilot.params.yaml

Review trace, required outputs and MultiQC. Use the pilot for engineering throughput and compatibility—not final duplication, coverage or biology.

34.18.10 Step 7: configure one complete-sample qualification

Do not use the cohort samplesheet yet. Select one representative complete paired sample and create a new production project root with separate work, results, logs and caches.

Create private production files:

cp conf/production.env.example conf/production.env
cp conf/production.shared.config.example conf/production.local.config
cp params/production.example.yaml params/one-sample.production.yaml

Edit every placeholder. The parameter file should resemble:

input: /storage/xxx/samplesheets/one-sample.csv
outdir: /storage/xxx/results/SAMPLE_001

aligner: bismark
fasta: /storage/xxx/reference/bismark_species_assembly/reference.fa
bismark_index: /storage/xxx/reference/bismark_species_assembly

Preflight using the production environment explicitly:

SITE_ENV=conf/production.env \
  bash bin/preflight.sh params/one-sample.production.yaml

Resolve every STOP and review every warning. Submit from the repository root:

mkdir -p logs
sbatch bin/run_production.sbatch params/one-sample.production.yaml

Do not call the repository qualified for your environment merely because the job started. Apply the complete-sample acceptance gate in this chapter.

34.18.11 Step 8: preserve the exact launch record

At submission, create a private run manifest and snapshot the submitted files:

mkdir -p /storage/xxx/run_manifests
cp assets/run-manifest.template.md \
  /storage/xxx/run_manifests/JOB_ID.run-manifest.md
cp /private/path/samplesheet.csv \
  /storage/xxx/run_manifests/JOB_ID.samplesheet.csv
cp /private/path/params.yaml \
  /storage/xxx/run_manifests/JOB_ID.params.yaml
sha256sum /storage/xxx/run_manifests/JOB_ID.samplesheet.csv
sha256sum /storage/xxx/run_manifests/JOB_ID.params.yaml
git rev-parse HEAD

Complete the manifest with the reference checksum, workflow revisions, container/software evidence, deviations, task trace and QC disposition.

34.18.12 Step 9: prepare the cohort only after qualification

When the representative full sample passes:

  1. replace pilot projections with measured full-sample runtime, peak RSS, CPU efficiency, I/O and storage;
  2. inspect sample-size variability across the cohort;
  3. review conf/production.local.config with the HPC team;
  4. choose concurrency that respects shared resources and controller wall-time;
  5. create a new unused cohort output directory;
  6. rerun preflight with the complete samplesheet; and
  7. submit the same pinned workflow/reference configuration.

The example policy limits Bismark alignment to ten concurrent samples. It is a starting point derived from one cluster and pilot—not a universal safe value. Sites with different node sizes, fair-share rules or memory must choose their own reviewed limit.

34.18.13 Step 10: monitor, resume and clean deliberately

Monitor the controller and task jobs:

bash bin/monitor_run.sh CONTROLLER_JOB_ID

If the controller or a task fails, diagnose before changing configuration. Relaunch the same run with the same work directory and -resume through the guarded launcher. Do not delete work/ while recovery or review remains possible.

Clean work data only after:

  • every required result and report is verified;
  • provenance and checksums are complete;
  • outputs have the required backup/retention protection;
  • no resume is expected; and
  • the exact cleanup target has been reviewed.

34.18.14 What users should customize—and what they should not

Customize for your project/site Keep stable unless deliberately revalidated
storage roots and cache paths biological process ordering
Java/container module names whole-sample deduplication semantics
scheduler account/partition policy pairing and samplesheet contracts
species/assembly FASTA and index reference/index identity requirement
samplesheet and output directory provenance and checksum requirements
reviewed CPU/memory/time/concurrency smoke → pilot → full-sample gates
optional methylseq parameters justified by assay pinned versions used for an accepted run

Do not edit cached nf-core pipeline source to make site-specific changes. Use parameters and layered configuration so the upstream revision remains identifiable and updateable.

34.18.15 Honest readiness statement

Before the complete-sample qualification finishes, the correct description is:

The companion repository provides a containerized, Slurm-ready and documented framework. Host bootstrap, the nf-core smoke test, the matching GRCh38 Bismark index and the 10M-pair real-data pilot have been demonstrated. Complete-sample production qualification is in progress.

After a user’s own complete representative sample passes all gates, they may state that the configuration was qualified in that specific environment for that reference, assay, workflow revision and acceptance procedure. They should not generalize that claim automatically to another cluster, species, pipeline version or regulated intended use.

34.19 What belongs in the public repository

Publish:

  • portable scripts and templates;
  • placeholder site configuration;
  • de-identified aggregate performance metrics;
  • assumptions and limitations;
  • scientific capacity figures; and
  • sanitized troubleshooting knowledge.

Do not publish:

  • credentials, tokens or private keys;
  • internal hostnames, accounts or topology;
  • institutional paths and support contacts;
  • raw FASTQs, BAMs or coverage files;
  • protected sample identifiers;
  • unreviewed MultiQC/logs containing private metadata; or
  • claims beyond the recorded evidence.

34.21 Decision record

The final production design was:

  • reuse nf-core/methylseq rather than reimplement Bismark orchestration;
  • use complete paired samples as the biological unit;
  • use containers for task software;
  • use Slurm per process task;
  • keep site paths and modules in ignored configuration;
  • pin workflow and Nextflow versions;
  • build one traceable index per species/assembly;
  • validate with smoke test, real-data pilot and one full sample;
  • cap Bismark alignment concurrency at ten for shared-resource fairness;
  • retain work/ until acceptance so -resume remains available; and
  • scale to 30 samples only after complete-sample MultiQC and resource review.

34.22 Try it yourself

34.22.1 Exercise 1: classify the evidence

Place each statement under measured, projected or pending:

  • pilot alignment peak RSS was 38.9 GB;
  • a complete sample will take exactly 6.5 days;
  • ten concurrent alignments may request 720 GB;
  • complete-sample duplication is acceptable.

Answer: measured; projected (and “exactly” is unjustified); calculated planning maximum; pending MultiQC review.

34.22.2 Exercise 2: design a safe chunk fallback

Draw the graph required if alignment must be chunked. It must include synchronized paired chunks, per-chunk alignment, completeness verification, BAM merge and sort, one global sample-level deduplication, methylation extraction and an equivalence test against an unsplit subset.

34.22.3 Exercise 3: review a production claim

A colleague says, “Slurm no longer shows the job, so methylation calling passed.” List the log, output, integrity, QC and provenance evidence still required.

34.23 What to remember

  • Installation success, pilot success and production validation are different claims.
  • Measure the dominant task before designing cohort concurrency.
  • Keep complete-sample deduplication global unless a validated alternative exists.
  • References are software inputs with versions and checksums, not generic folders.
  • One sample creates many workflow tasks and scheduler jobs.
  • Preserve cache and provenance until outputs pass acceptance.
  • Public documentation should retain engineering knowledge without exposing private infrastructure or data.
