4  HPC mental model: nodes, schedulers, software and storage

By the end of this chapter, you will be able to:

  • explain why a cluster has login nodes, compute nodes and a scheduler;
  • distinguish submission, allocation, execution and scientific success;
  • reason about CPU, memory, elapsed-time and concurrency requests;
  • explain what module purge and module load change;
  • predict how modules and Conda can compete through PATH;
  • choose among home, project and scratch storage deliberately;
  • interpret sinfo, squeue, sacct, quota and filesystem evidence;
  • review an AI-generated batch script before submitting it; and
  • produce a sanitized hpc-inventory.txt for debugging and interviews.

4.1 Why a biologist should care

A laptop usually has one user making immediate decisions. An HPC cluster is a shared system where many users compete for finite processors, memory, storage bandwidth and accelerators. The scheduler must decide where and when work runs.

That changes the meaning of familiar actions:

  • starting a program is not the same as submitting a job;
  • requesting 32 CPUs does not make single-threaded software use 32 CPUs;
  • a job marked COMPLETED may still have produced invalid biological output;
  • a file can be on a large filesystem while the user’s quota is exhausted;
  • software can exist on the cluster but remain invisible until a module is loaded; and
  • activating Conda does not reserve any compute resources.

AI can draft a batch script in seconds. It cannot know unwritten site policy, your allocation, your data governance requirements or the real resource profile of your sample unless you provide and verify that context.

4.2 Engineering objective

The goal is to build an execution model you can interrogate:

your terminal
    │ SSH
    ▼
login node ── submits a resource request ──► scheduler
    │                                         │
    │ inspect/edit/light work                 │ grants allocation
    │                                         ▼
shared storage ◄──────────────────────── compute node
  home / project / scratch                runs the task

The scheduler controls compute placement. The filesystem carries scripts, inputs, work directories, logs and outputs between the nodes.

4.3 The four states people accidentally collapse into one

An interview-quality explanation separates these states:

  1. Submitted: the scheduler accepted a job description and assigned an ID.
  2. Pending: the job is waiting for resources, priority, dependencies or a policy condition.
  3. Running: commands are executing inside an allocation.
  4. Completed: the scheduler received a zero process exit status.

None of those alone proves that the correct sample, reference, parameters or outputs were used. Scientific validation is a separate layer.

4.4 Before you type: identify the site and policy

Never assume that commands from another institution are valid locally. Find the site documentation or ask an administrator:

  • What scheduler is used: SLURM, PBS, LSF or something else?
  • What partitions or queues may your account use?
  • Which project or billing account should jobs charge?
  • Where should large inputs, caches, temporary work and final results live?
  • Are login-node CPU, memory and time limits enforced?
  • Which container runtime is supported?
  • How are protected or regulated datasets governed?

This chapter uses SLURM syntax and DLDCC examples. The mental model is portable; the names main, waterland and java/jdk-18.0.1.1 are not.

4.5 Connect through SSH

A typical connection has this shape:

ssh username@login.cluster.example.org

SSH authenticates the user and creates a remote shell. It does not reserve a compute node. Verify the new context:

hostname
whoami
pwd

The prompt may include a host name, but scripts should use explicit evidence such as hostname rather than parsing decorative prompt text.

WarningDo not publish cluster access details

A tutorial may show a generic login pattern. Do not commit private keys, passwords, one-time codes, internal host inventories or access tokens. Whether a hostname is public is an institutional decision.

4.6 Login nodes are coordination nodes

Appropriate login-node work usually includes:

  • editing scripts and configuration;
  • inspecting small text files and job logs;
  • managing Git repositories;
  • submitting, monitoring and cancelling jobs;
  • transferring modest files through approved methods; and
  • performing lightweight environment checks.

Compute-intensive alignment, large compression jobs, broad recursive scans and workflow execution belong in an allocation. A login node is shared by many people; one uncontrolled process can degrade everyone’s session.

The line is set by local policy, not by a universal number of seconds or gigabytes.

4.7 Compute nodes and allocations

A compute node contributes resources such as:

  • CPU cores or hardware threads;
  • RAM;
  • local temporary storage;
  • GPUs or other accelerators; and
  • access to shared filesystems and high-speed networking.

An allocation is permission to use a specified resource bundle for a limited time. It can be interactive or batch-oriented.

Interactive allocations are useful for small debugging sessions when the site permits them. A common SLURM pattern is:

srun \
  --partition=<partition> \
  --account=<account> \
  --cpus-per-task=2 \
  --mem=4G \
  --time=00:15:00 \
  --pty bash

Angle-bracket values are placeholders. Site documentation may require salloc followed by srun, or prohibit interactive jobs in some partitions.

Batch jobs are preferable for reproducible work because the request and command can live in a reviewed file.

4.8 Scheduler vocabulary

Term Meaning Common misunderstanding
Cluster The complete shared computing system One giant computer
Node One computer within the cluster One CPU core
Partition A scheduler grouping of nodes and policy A disk partition
Account Project/allocation charged for usage Unix login name
QOS A policy class affecting limits or priority Scientific quality score
Job A submitted resource request plus commands Guaranteed successful analysis
Task A unit of work within a job Always one biological sample
Job array Repeated job template indexed over items Automatic workflow dependency graph

SLURM’s official quick-start guide is the authoritative command reference. Your site documentation determines which options are permitted.

4.9 Inspect the cluster without submitting work

4.9.1 Partitions and nodes with sinfo

sinfo

A compact site-specific view might be:

sinfo -o '%P|%a|%l|%D|%c|%m'

The fields request partition, availability, time limit, node count, CPUs and memory. Output formats and configured values vary by SLURM version and site.

Read the evidence as policy and capacity, not a promise that resources are immediately available.

4.9.2 Your jobs with squeue

squeue --me

If the installed SLURM version lacks --me, use:

squeue -u "$USER"

Important state codes include:

  • PD: pending;
  • R: running;
  • CG: completing; and
  • site- or version-dependent failure/hold states.

For a pending job, inspect the reason column before changing the request. A job waiting for resources is different from one held for an invalid account.

4.9.3 Historical evidence with sacct

sacct \
  --starttime today \
  --user "$USER" \
  --format=JobID,JobName,Partition,State,ExitCode,Elapsed,AllocCPUS,MaxRSS

Accounting fields depend on site configuration. MaxRSS may be delayed or absent. A COMPLETED state and 0:0 exit code mean the scheduled process reported success; inspect application logs and outputs next.

4.10 Resource requests are engineering hypotheses

4.10.1 CPUs

In a typical single-program job:

#SBATCH --cpus-per-task=4

This allocates four CPUs to one task. The application must also be configured to use four threads:

tool --threads "$SLURM_CPUS_PER_TASK"

If the tool is single-threaded, most allocated CPUs remain idle. If the tool silently starts more threads than allocated, it can oversubscribe the node.

4.10.2 Memory

These requests are not interchangeable:

#SBATCH --mem=8G

requests memory for the job allocation on a node, whereas:

#SBATCH --mem-per-cpu=2G

scales memory with allocated CPUs. Exact semantics should be checked against site policy, especially for multi-node jobs.

Requesting far too little causes out-of-memory failure. Requesting far too much can delay scheduling and waste charged capacity. Start from test data or prior accounting evidence, then revise with margin.

4.10.3 Time

#SBATCH --time=00:30:00

This is a maximum wall-clock duration, not predicted CPU time. A job that exceeds it is terminated. A grossly inflated time request may make backfilling harder and delay the job.

4.10.4 Concurrency

These are different scaling dimensions:

  • threads: one process uses several CPUs;
  • processes: several programs run at once;
  • samples: workflow tasks may execute concurrently;
  • nodes: a distributed program spans computers.

Giving every task all available CPUs can reduce total throughput when many samples could have run simultaneously. Industry interviews often probe this tradeoff.

4.11 Read an AI-generated batch script critically

Consider this small template:

#!/usr/bin/env bash
#SBATCH --job-name=inventory-test
#SBATCH --partition=<partition>
#SBATCH --account=<account>
#SBATCH --cpus-per-task=2
#SBATCH --mem=2G
#SBATCH --time=00:05:00
#SBATCH --output=logs/%x-%j.out
#SBATCH --error=logs/%x-%j.err

set -euo pipefail

printf 'job_id=%s\n' "$SLURM_JOB_ID"
printf 'node=%s\n' "$(hostname)"
printf 'cpus=%s\n' "$SLURM_CPUS_PER_TASK"

Before submission, the human reviewer must answer:

  1. Do the partition and account exist and permit this job?
  2. Does logs/ exist before SLURM tries to open the output files?
  3. Is Bash available at the resolved interpreter path?
  4. Are two CPUs and 2 GB justified by the command?
  5. Are all required input paths visible from compute nodes?
  6. Will shell initialization, modules or Conda be established explicitly?
  7. Could any printed value expose sensitive information?
  8. What output proves that the intended program ran?

Create the log directory before submission:

mkdir -p logs
sbatch inventory-test.sh

Submission output such as Submitted batch job 123456 proves only scheduler acceptance.

4.12 Environment Modules: controlled shell transformations

Clusters may install several versions of Java, compilers and applications. The module system exposes a selected version by modifying environment variables. The Lmod user guide describes this behavior.

Common inspection commands are:

module avail
module list
module show java/<site-version>

Common state changes are:

module purge
module load java/<site-version>
module load singularity/<site-version>

module purge unloads module-managed state. It does not uninstall software or delete files. module load does not copy the application into your home directory; it changes variables so the shell can find a site installation.

Many module commands print to standard error even when successful. Capture both streams when creating evidence:

module list > loaded-modules.txt 2>&1

4.12.1 Prove what a module changed

printf '%s\n' "$PATH" > path-before-module.txt
command -v java > java-before-module.txt 2>&1 || true

module load java/<site-version>

printf '%s\n' "$PATH" > path-after-module.txt
command -v java > java-after-module.txt 2>&1 || true

diff -u path-before-module.txt path-after-module.txt || true
diff -u java-before-module.txt java-after-module.txt || true

The final || true is appropriate here because diff returns 1 when files differ—the condition we are intentionally investigating.

4.13 Modules and Conda are separate mechanisms

This is the most important Chapter 4 distinction.

module load java/... ──► edits PATH and related variables

conda activate project ─► edits PATH and sets CONDA_PREFIX

shell resolves `java` ──► first matching executable in current PATH wins

module purge does not deactivate a Conda environment. conda deactivate does not unload a Java module. However, both operations can rearrange PATH, so the winning executable may change.

Inspect state rather than trusting the prompt:

printf 'CONDA_PREFIX=%s\n' "${CONDA_PREFIX:-NOT_ACTIVE}"
module list 2>&1
type -a java
command -v java
java -version

Order matters. If a Conda environment contains Java and is activated after the module, Conda may win. If the module prepends its Java directory later, the module may win. A pipeline should make this choice explicit.

ImportantActivation is not allocation

Loading a module or activating Conda changes the software environment in the current shell. Neither action requests CPU, memory or a compute node from SLURM.

4.14 Singularity/Apptainer: the cluster container layer

Sites commonly provide either singularity or apptainer:

command -v singularity
singularity --version

command -v apptainer
apptainer --version

They are related HPC-oriented container runtimes, but names, versions and site configuration differ. Do not alias one name to the other without understanding the installation.

SingularityCE is designed for shared systems and normally preserves the user’s identity inside the container. Its SIF format packages a container as a single file. The official SingularityCE user guide explains its privilege and runtime model.

A container packages user-space software. It does not package the host kernel, SLURM allocation, filesystem permissions or data-governance policy. Chapter 19 develops this boundary in depth.

4.15 Storage is a resource, not just a path

Typical storage classes have different purposes:

Storage Typical use Typical risk
Home Small configuration, scripts, keys Tight quota; backed up but not high-throughput
Project Shared inputs, references, durable results Group quota; can become globally full
Scratch Temporary workflow work and large intermediates Purged; not backed up
Node-local temporary Short-lived task-local I/O Disappears when job ends; must stage outputs back

These are common patterns, not promises. Verify your site.

4.15.1 Capacity versus quota

df reports filesystem capacity:

df -h "$HOME"
df -h /path/to/project

du estimates space used by visible files under a path:

du -sh "$HOME/.nextflow" 2>/dev/null || true
du -sh /path/to/project/work 2>/dev/null || true

quota may report a user or group limit:

quota -s

A filesystem can show hundreds of gigabytes free while your personal quota is zero. Conversely, your quota can allow growth while the shared filesystem is nearly full. Inode exhaustion can also prevent new files even when byte capacity remains.

4.15.2 Match data lifetime to storage lifetime

  • Keep Git-tracked code and small configuration in durable storage.
  • Put reusable reference data in an approved shared location.
  • Put Nextflow work directories and large caches where performance, quota and cleanup policy allow.
  • Publish final evidence out of scratch before purge deadlines.
  • Never use scratch as the only copy of irreplaceable data.

4.16 DLDCC case study: real evidence, site-specific values

The companion project was validated on the DLDCC cluster at Baylor College of Medicine in August 2026. The following values are a historical snapshot, not portable defaults:

partition: main
account: waterland
container runtime: SingularityCE 4.0.3
Java module: java/jdk-18.0.1.1

The workflow later succeeded through SLURM with five separate tasks. The trace recorded native job IDs, CPU utilization, peak RSS and elapsed time.

Three failures teach more than the successful command.

4.16.1 Failure 1: Java existed but its default garbage collector crashed

The site Java executable was found, yet initialization failed inside the G1 garbage collector. The verified workaround was:

module purge
module load java/jdk-18.0.1.1
export NXF_OPTS='-XX:+UseSerialGC'
java $NXF_OPTS -version

Lesson: command -v java proves resolution, not runtime health. Test the runtime independently and record unusual JVM options.

4.16.2 Failure 2: filesystem free space did not prevent a quota error

Nextflow attempted to place its framework JAR under the default home cache and failed with Disk quota exceeded. The partially written JAR then appeared corrupt.

The fix was to place Nextflow state on approved project storage:

export NXF_HOME="$PWD/.nextflow"

Lesson: diagnose the first write failure before replacing the application. A corrupt cache file can be a downstream symptom of quota exhaustion.

4.16.3 Failure 3: the container had tools but lacked ps

The workflow tools ran in the image, but Nextflow’s task-metrics wrapper also needed ps. The first containerized run failed with:

Command 'ps' required by nextflow to collect task metrics cannot be found

Adding procps-ng to the image fixed the runtime contract.

Lesson: a process needs both scientific executables and orchestration support. An AI-generated dependency list based only on the pipeline commands may be incomplete.

4.17 Build hpc-inventory.txt

Run this from a directory approved for small diagnostic files. It performs read-only inspection:

{
  printf '=== IDENTITY ===\n'
  date
  printf 'user=%s\n' "$USER"
  printf 'host=%s\n' "$(hostname)"
  printf 'cwd=%s\n' "$PWD"
  printf 'shell=%s\n' "$SHELL"

  printf '\n=== MODULES ===\n'
  module list 2>&1 || true

  printf '\n=== COMMAND SOURCES ===\n'
  for command_name in java conda singularity apptainer sbatch squeue sacct; do
    if command -v "$command_name" >/dev/null 2>&1; then
      printf '%-12s %s\n' \
        "$command_name" \
        "$(command -v "$command_name")"
    else
      printf '%-12s NOT_FOUND\n' "$command_name"
    fi
  done

  printf '\n=== ACTIVE CONDA ===\n'
  printf 'CONDA_PREFIX=%s\n' "${CONDA_PREFIX:-NOT_ACTIVE}"

  printf '\n=== SCHEDULER ===\n'
  sinfo -o '%P|%a|%l|%D|%c|%m' 2>&1 || true
  squeue -u "$USER" 2>&1 || true

  printf '\n=== STORAGE ===\n'
  df -h "$HOME" 2>&1 || true
  quota -s 2>&1 || true
} > hpc-inventory.txt

Read the syntax conceptually:

  • the outer braces group output into one report;
  • 2>&1 includes diagnostic streams;
  • the loop applies one lookup policy consistently;
  • ${CONDA_PREFIX:-NOT_ACTIVE} provides an explicit fallback; and
  • || true allows optional site commands to be absent without truncating the inventory.

|| true is not appropriate for scientific processing steps whose failure must stop the workflow.

4.18 Sanitize before sharing

Inspect:

less hpc-inventory.txt

Remove or replace:

  • internal hostnames if policy treats them as sensitive;
  • private project paths;
  • usernames when unnecessary;
  • account or allocation names not approved for publication; and
  • any accidental credential or patient-data reference.

Do not collect env, shell history, SSH configuration or key contents for this artifact.

4.19 Verification checkpoint

test -s hpc-inventory.txt
printf 'inventory_nonempty=%s\n' "$?"

grep -q '^=== IDENTITY ===' hpc-inventory.txt
printf 'identity_section=%s\n' "$?"

grep -q '^=== COMMAND SOURCES ===' hpc-inventory.txt
printf 'command_sources_section=%s\n' "$?"

grep -q '^=== SCHEDULER ===' hpc-inventory.txt
printf 'scheduler_section=%s\n' "$?"

grep -q '^=== STORAGE ===' hpc-inventory.txt
printf 'storage_section=%s\n' "$?"

All five values should be zero. The deeper pass condition is verbal: point to the lines identifying Java, Conda, the container runtime, scheduler and storage, then explain who manages each one.

4.21 Hands-on exercise: review a dangerous AI suggestion

An AI assistant proposes this command on a shared login node:

module load java
conda activate analysis
nextflow run main.nf \
  --reads '/project/patient-data/*.fastq' \
  -with-docker \
  -process.cpus 64 \
  -process.memory 240.GB \
  -resume &

Write ai-review.md with at least twelve findings. Classify each as:

  • site-policy unknown;
  • execution-model error;
  • resource assumption;
  • software-environment ambiguity;
  • data/privacy risk; or
  • verification gap.

Your review must address:

  1. login node versus scheduler allocation;
  2. whether Docker is available or permitted;
  3. module version ambiguity;
  4. module/Conda Java precedence;
  5. unverified partition, account and QOS;
  6. blanket CPU and memory requests;
  7. quoting and wildcard responsibility;
  8. protected-data path disclosure;
  9. detached background execution;
  10. -resume cache assumptions;
  11. missing logs, reports and exit-status capture; and
  12. absence of scientific output validation.

Then write a decision tree, not merely a corrected command:

If this is the login node → submit through the approved scheduler profile.
If the site supports Singularity → use the validated SIF/profile.
If Java comes from a module → verify its path and runtime before Nextflow.
If inputs are protected → follow approved storage and logging policy.
If resources are unknown → profile a small representative test first.
TipExercise reasoning hints

A strong review does not invent the correct partition or account. It identifies missing evidence and states how to obtain it. It also distinguishes operational success from scientific validation.

For every AI-generated line, ask:

What assumption does this line make?
Who owns that decision?
What evidence would falsify the assumption?
What damage follows if it is wrong?
How will success be verified?

4.22 Interview grill: ten hard questions

Answer aloud before opening the model points. These are intentionally scenario-based.

  1. A job remains pending for two hours with reason Resources. What evidence do you inspect before requesting more resources or changing partitions?
  2. A four-thread aligner receives --cpus-per-task=16. Describe the possible effects on utilization, queue time, throughput and accounting.
  3. module purge was run, but the prompt still shows a Conda environment. Is that contradictory? How do you prove which Java will run?
  4. df -h shows 700 GB free, yet Nextflow reports Disk quota exceeded and later reports a corrupt JAR. Construct the causal explanation.
  5. A SLURM job is COMPLETED with exit code 0:0, but the BAM contains zero mapped reads. Which system succeeded, which validation failed, and what do you inspect next?
  6. Why might requesting the maximum CPU and memory for every Nextflow process reduce total pipeline throughput?
  7. Explain why a container can contain Bowtie2 and SAMtools yet a Nextflow task still fail because ps is missing.
  8. An AI generates a Docker-based launch command for an HPC login node. What questions must be answered before translating it to Singularity/Apptainer?
  9. When would you choose node-local temporary storage over shared project storage, and what correctness risk must the job handle?
  10. Design the minimum evidence package for escalating an intermittent HPC job failure without exposing protected data or credentials.
NoteModel answer points
  1. Inspect squeue reason and job details, partition availability, requested shape, priority/QOS/account validity and similar recent jobs. Resources means the current request cannot yet be placed; it does not automatically mean the request is too small.
  2. The aligner may use only four CPUs while twelve sit idle. The larger shape can wait longer, reduce how many samples run concurrently and increase charged allocation without reducing runtime. Confirm whether other pipeline work shares the task before reducing it.
  3. No. Modules and Conda are independent state mechanisms. Inspect CONDA_PREFIX, module list, type -a java, command -v java and java -version; the first matching path wins.
  4. Filesystem capacity and user quota are different limits. The initial write was truncated when the user’s quota was exhausted; the corrupt-JAR error is a downstream symptom. Fix cache placement/quota and replace the incomplete artifact only after verifying its exact target.
  5. SLURM successfully ran a process that reported zero. Biological/QC expectations failed. Inspect the aligner log, reference identity, read pairing, parameters, BAM header, flagstat/idxstats and input checksums.
  6. Oversized tasks occupy scarce nodes, wait for a harder-to-place resource shape and prevent concurrent samples from using otherwise available cores. Throughput depends on the whole task graph, not one task’s maximum size.
  7. Nextflow wraps the scientific command to stage files, capture status and collect metrics. The wrapper’s runtime dependencies are part of the container contract even when they are not biological tools.
  8. Confirm site runtime/version, OCI compatibility, image provenance, bind paths, clean-environment behavior, user identity, GPU/MPI needs, registry access, cache placement and whether building/pulling is permitted on the cluster.
  9. Use node-local storage for high-throughput disposable intermediates when shared I/O is a bottleneck. The job must stage inputs in and validated outputs out before termination; node-local data can disappear without recovery.
  10. Include sanitized job ID, timestamps, state/exit code, resource request, relevant accounting metrics, module/runtime versions, container digest, command log with protected paths redacted, small non-sensitive reproducer and validation results. Exclude tokens, keys, full environment dumps and patient identifiers.

4.23 What to remember

  • A login node coordinates work; a scheduler allocation authorizes heavy work.
  • Resource requests are hypotheses to validate with measurement.
  • Modules and Conda are independent, but both can change executable precedence.
  • Filesystem capacity, quotas, inodes and retention policies are different constraints.
  • Scheduler success is not scientific success.
  • AI may draft syntax; the human remains responsible for site policy, resource reasoning, privacy and verification.
